# Containers — 需求

话题与合并转发都是「一条消息装着一串消息」。两者在消息列表里各占一行摘要，内容在右栏展开；右栏可以逐层深入，逐层退回。

## 背景

飞书有两种消息本身不是内容，而是别的消息的容器：

- **话题**（`thread_id`）：一条根消息加若干回复。回复是本会话的新消息，有自己的 `message_id`，`message_position` 为负。
- **合并转发**（`msg_type = merge_forward`）：转发时打包的一串历史消息。子消息**不是副本**，是源会话里那些消息本身——同一个 `message_id`，同一个源 `chat_id`。

larkim 今天对这两者的处理方向相反，而且都不对。

合并转发**逐字打印**。`messages.content` 存的是 lark-cli 渲染出的整棵树，带字面的 `<forwarded_messages>` 标签、每条子消息一行 `[2026-09-24T18:51:02+08:00] 张三:` 加四空格缩进的正文，嵌套转发再缩四格。消息列表把它原样吐出来：一条平均 746 字符、最长 2644，能吃掉几十行，读的人要在标签和 ISO 时间戳之间找正文。缺口早已记录在案——合并转发常常是整条消息的正文，现在必须跳客户端才能读。

话题回复**散在主流里**。回复按自己的时间插在主消息流中间，和普通消息没有任何视觉差别；根消息只有一个不带计数的 `⤷thread` 徽章。飞书客户端不是这样：回复收在根消息的框里，主流只看得到根，根上写着「还有 18 条回复」。

两个缺口的解法是同一个：容器在列表里只占一行，内容进右栏。而右栏今天是话题 / 助手 / 会话名片三选一的分时槽，装不下「从话题里打开一条合并转发，再打开它嵌套的那层」——所以右栏要能叠。

## 验收标准

1. 合并转发在消息列表里只占一行，看不到 `<forwarded_messages>` 字样，也看不到 ISO 时间戳。
2. 点它，右栏列出子消息，其中的图片照常显示。
3. 点嵌套转发的摘要行，右栏再叠一层；`Esc` 逐层退回，最后一层退掉时右栏关闭。
4. 话题根只占一行并带回复数；回复不再出现在主消息流；点开进右栏。
5. 窄屏（右栏顶替消息面板时）重复第 3 条，`Esc` 仍逐层退回。
6. 话题里留一条未读回复：打开会话不清它，打开话题才清。
7. 转发引用了已退出的会话：摘要说明无法展开，点击给出提示而不是空面板。
8. 搜索或 `:mentions` 命中一条话题回复：落地后右栏压开那条话题，光标停在命中的那条回复上。
9. 我回复过的话题来了新回复：摘要行起一个未读圆点，会话列表那一行也起一个记号；我没参与过的话题两处都不起。
10. 一条既是合并转发、又被人开了话题的消息：主流画话题摘要；进话题帧后它本身是一行转发摘要，再点压下一层。

## 行为

### 列表里的摘要

容器的正文**只占一行**，与会话列表给一条消息的待遇一致：数量加一条代表性内容，整行一个点击目标。

```
张三  hello
      ⤷ 23 条回复 · 李四: 1234

李四  在看了
      ⤷ 还没有回复

王五  [合并转发] 5 条 · 张三: hey
```

代表的那一条方向相反：合并转发取**最前**的子消息，话题取**最后**的回复。转发是冻结的，开头是它被转发的语境；话题是活的，最新那句才是当前状态。

话题根没有回复时摘要行仍在。它是进话题去回复的入口，没有它读者无从知道这条消息按 `Enter` 会开话题而不是回复它。

合并转发还没被展开时只画 `[合并转发]`，不写数量：数量要等子消息落地才数得准，先写一个数再改成另一个比不写更糟。展开被拒的画 `[合并转发] · 无法展开`。

### 打开与退回

| 动作 | 结果 |
|---|---|
| 单击摘要行 | 在右栏打开该容器，叠在当前内容之上 |
| `Enter` / `t`（光标在容器上） | 同上 |
| `Esc`（焦点在右栏） | 退回一层；已是最后一层则关闭右栏 |

助手与会话名片不参与叠放：打开它们会清空右栏原有内容。它们讲的是整个会话，不属于任何容器。

右栏里 `Enter` 的含义随当前层而变：话题层是「在话题内回复」，转发层是「打开选中的嵌套转发」。合并转发只能读不能回，飞书的接口也只允许应用身份创建合并转发。

`r`、`R`、`e`、`f`、`y` 系列作用在容器上时照旧：容器是本会话的一条真实消息，能引用回复、能加表情、能转发、能复制。被容器语义占掉的只有 `Enter` 与 `t` 这一个「打开」动作。

一条消息可以同时是两种容器——一条合并转发被人开了话题。主流画话题摘要，活的那个赢；进话题帧后根消息本身是一行转发摘要，点它再压一层。层级与客户端一致：话题里包着转发。

### 折叠后的未读

话题回复本来就不计入会话的未读数、不点亮 `@` 徽章——这一点折叠前后一致。

变的是两处。

**清除时机。** 折叠前打开会话就把回复一并记为已读，因为页面确实把它们摆在了读者面前；折叠后页面看不到它们，所以打开会话不再清，打开话题才清。打开即清整条，不要求读者滚到底：话题是一屏的东西，不是会话。

**可见性。** 回复离开主流后，读者需要一个知道「哪条话题里有新东西」的地方。摘要行起一个未读圆点，会话列表那一行起一个 `⤷`。两处都不报数、不改会话列表的排序，`n` / `N` 也不走它们——`n` 的队列是徽章那一份，多一级就不再是「清队列」。

只有**我参与过**的话题才亮：我在里面说过话（根消息算我的话），或者有人在里面 `@` 我。大群里与我无关的话题不该把主流点成一片，那正是未读徽章当初排除回复要避的效果。

### 子消息的来源

合并转发的子消息由同步进程展开后落到本地，所以打开是即时的，断网也能读。子消息不进 `messages` 表——它们是源会话里那些消息本身，写进去会覆盖那些会话的真实数据。

还没轮到的转发，读者点开时即时取一次：帧先开，内容到了就地填上。

### 落地与跳转

搜索、`:mentions` 与引用跳转落到一条已折叠的话题回复上时，右栏压开那条话题并在帧内选中它——命中的是那条回复，交给读者的就该是那条回复。这一下按「看见」算，整条话题随之结算，与跳转落地清掉未读点是同一条规矩。

## 边界

- 不能**创建**合并转发：飞书只对应用身份开放该接口。
- 不做通用的「跳回来」返回栈。右栏的叠放是容器的打开层级，逐层进、逐层出；引用跳转仍然是单向的，与此无关。
- 转发内容在帧里不做缩进渲染：每层一个面板，嵌套的那层是一行摘要，点进去才展开。
- 子消息不可回复、不可加表情、不可撤回——它们不属于当前会话。
- 摘要固定一行，不随窗口高度展开成多行。
- 搜索命中转发**内部**的文字时，落地停在那条转发上，不自动展开、不定位到句：命中说的是「在这条转发里」，往下找是读者的事。
- 不改变话题回复与转发在搜索结果、`larkim messages`、`:copy` 和 agent 上下文导出里的行为。屏幕为人而折叠，导出给的仍是内容本身；`yc` 同理，复制一条转发得到的是它的全文。
- 撤回一条合并转发只标记它，已落地的子消息照旧留着，与 `content` 的处理一致。
