# Read sync — 需求

larkim 里读过的会话，飞书桌面端的红点跟着落下来。

## 背景

读状态此前只有一个方向：飞书 → larkim。`read_state.is_read_remote` 由轮询拉回，翻转的时机是用户在飞书客户端里看过那条消息；`local_read_at` 补上另一半，让在 larkim 里读过的会话徽标能落下来，因为飞书 OpenAPI 没有 mark-read。

反方向是空的，代价落在客户端那一侧：在 larkim 里读完一屏，飞书的红点原样亮着，Dock 角标照样堆。`docs/chats-list/PRD.md` 的验收标准是「扫一眼 larkim 的会话列表就能分活，不必切回飞书客户端确认」——这条在 larkim 侧成立，却把飞书的角标变成了一个只能靠定期回去点一遍才消得掉的噪声源。

飞书没有把会话标记为已读的接口。唯一能让客户端发出已读回执的杠杆是 applink：`lark://applink.feishu.cn/client/chat/open?openChatId=<id>`，用 `open -g` 投出去，客户端导航到该会话而不抢走屏幕。

## 验收标准

1. 在 TUI 里进入一个有未读的会话，飞书客户端该会话的红点消失、Dock 计数下降。
2. 全程 larkim 不失焦：飞书窗口不前置、不切 Space，键盘焦点留在终端。
3. 会话没有未读时不投 applink；用 `j`/`k` 在列表上掠过不投。
4. 停在一个活跃会话里、视野在消息流末尾时持续收消息，每条新消息把红点重新点亮，红点随消息到达的那一页再次落下。
5. 在会话里往上翻历史时落进来的消息不算读：会话列表的未读数继续涨，飞书红点保持亮，消息上带未读标记。滚回末尾时一并落下。
6. 终端失焦时落进来的消息同样不算读，回到终端、且视野在末尾时才落。
7. 一次动作就能把整份列表的红点清掉：按下后飞书客户端依次走过每个还欠着的会话，Dock 归零，larkim 不失焦。

## 行为

- **触发**：会话页面正摆在读者眼前、且页面上还有没收下的未读时，把这批未读记为本地已读并投出该会话的 applink。「摆在眼前」是终端有焦点、消息面板停在消息流末尾、没有搜索/Mentions 面板或帮助层盖住它、终端也没窄到把它折叠掉。进入会话、开着的会话里落入新未读、从历史滚回末尾、切回终端，走的都是这一条路径——客户端的红点随每条新消息重新亮起，清红点不是一次性动作。
- **未读的判据**：投不投 applink 看 `is_read_remote = 0`、`local_read_at = 0`、非 thread 回复、未撤回，与这次访问记为已读的那一批**相等**——静音的消息两边都在内，见 [silence](../silence/TECH.md)。会话列表的徽标在此之上再排掉静音的，所以徽标是 0 的会话这里仍可能有红点要清。thread 回复两边都不算：会话页把它们折进根消息那一行，页面上一条都没有，它们由打开话题面板时结算。判断读的是页面查询时的状态，不是当前徽标——本次访问自己的写入会把徽标抹成 0。
- **投出次数**：由未读消息条数决定，不由重载次数决定，也不由视野来回滚动的次数决定。每次投出对应的那批未读会在同一时刻被记为本地已读，下一页因此不再命中。
- **焦点**：applink 一律以后台方式投出。`o` 键是另一回事——它是「我要去飞书」，照常前置窗口。
- **失败**：`open` 失败时在状态行提示。红点没落下不影响 larkim 自己的徽标，`local_read_at` 已经写好了。

## 批量

会话列表表头右侧有一个双勾按钮，命令行有 `:read-all`，CLI 有 `larkim read-all`。三个入口同一条路径：先查出还欠着的会话，再把**所有**未读（thread 回复也在内）记为本地已读，然后依次投出这些会话的 applink。

- **先问后做**：TUI 在状态行问 `mark N chats read? y/n`，`y` 以外一律取消；这是仅次于撤回的第二个要确认的动作，因为它不可撤销且会驱动客户端走过几十个会话。CLI 由显式敲下的命令本身充当确认，`--dry-run` 只数不写。
- **按钮常驻**：不按未读数开关。表头的上标数字把免打扰排除在外、徽标查询把本地静音排除在外，按任何一个开关都会在「只剩这两类未读」时恰好把按钮收走——而那正是最想按它的时刻。没有东西可清时按下回一句 `nothing waiting in Feishu`。
- **落点**：每条 applink 带上该会话最新一条仍欠着的消息，让客户端落在末尾而不是它自己的未读分隔线上。
- **集合**：主消息流里仍欠着的会话。thread 回复不构成投出理由（见边界），本地照样记为已读。免打扰与本地静音都不影响这个集合——它们决定要不要打扰读者，不决定飞书那边还亮不亮。
- **一次性**：写完之后这批会话不再进集合，失败的那几个也不重试——本地已读同时把它们挡在 read-status 轮询之外，客户端那边的红点就留着，直到该会话来了新消息才有下一次投出。所以宁可报出「N 个没清掉」，也不要悄悄吞掉。
- **收尾**：读者当前打开的会话排在最后，客户端因此停在终端所在的地方。

## 投出的节奏

所有 applink 走同一条队列，固定间隔逐条投出。客户端只有一个，同时投两条会把还在飞的那次导航顶掉——批量清理与读者自己的导航正是两个写者。

队列只延后、不丢弃：投出次数仍由未读消息条数决定。冷却窗口是另一回事，它会让落在窗口内的消息被本地已读静静收掉、applink 再也不投，因此不做。

`Esc` 停下进行中的批量清理，清空它的队列。读者自己导航带出的那一条不在此列：本地已读已经落了，丢掉它就等于上面否掉的冷却窗口。

## 边界

- **thread 回复的红点清不掉。** applink 打开的是会话主消息流，客户端不会因此渲染 thread 内的回复，回执也就不翻。larkim 的徽标本来也不计 thread 回复，两边口径一致；chat 消息流里混着的 thread 回复因此不作为投出 applink 的理由。
- **飞书客户端的「当前会话」会跟着 TUI 走。** 切回飞书时停在最后清过红点的那个会话；批量清理结束时那是读者自己所在的会话。
- **跳到历史中间不算读。** 从搜索命中或 `:mentions` 跳进会话、光标落在一条旧消息上时，它下方的未读照旧亮着；滚到末尾才落。
- **未读标记比未读数活得久。** 滚回末尾把会话记为已读之后，消息上的 `●` 仍留着，直到光标走过那一块——与打开会话时的行为一致，这样标记不会在读者眼皮底下熄灭。
- **不做「N 条新消息」浮标。** 会话列表的未读数一直在视野里，已经回答了「下面还有没有东西」；面板底部再加一个跳转浮标是客户端的表现形式，不是它的语义。
- **客户端没在运行时 applink 会把它拉起来。** 桌面端常驻是这个工具的前提，不为此做探测。
- **无配置开关。** 自动清红点是「读了」的一部分，不是一个可选动作；批量清理是一个显式动作，所以有入口而没有开关。
