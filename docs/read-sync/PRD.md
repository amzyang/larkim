# Read sync — 需求

larkim 里读过的会话，飞书桌面端的红点跟着落下来。

## 背景

读状态此前只有一个方向：飞书 → larkim。`read_state.is_read_remote` 由轮询拉回，翻转的时机是用户在飞书客户端里看过那条消息；`local_read_at` 补上另一半，让在 larkim 里读过的会话徽标能落下来，因为飞书 OpenAPI 没有 mark-read。

反方向是空的，代价落在客户端那一侧：在 larkim 里读完一屏，飞书的红点原样亮着，Dock 角标照样堆。`docs/chats-list/PRD.md` 的验收标准是「扫一眼 larkim 的会话列表就能分活，不必切回飞书客户端确认」——这条在 larkim 侧成立，却把飞书的角标变成了一个只能靠定期回去点一遍才消得掉的噪声源。

飞书没有把会话标记为已读的接口。唯一能让客户端发出已读回执的杠杆是 applink：`lark://applink.feishu.cn/client/chat/open?openChatId=<id>`，用 `open -g` 投出去，客户端导航到该会话而不抢走屏幕。

## 验收标准

1. 在 TUI 里进入一个有未读的会话，飞书客户端该会话的红点消失、Dock 计数下降。
2. 全程 larkim 不失焦：飞书窗口不前置、不切 Space，键盘焦点留在终端。
3. 会话没有未读时不投 applink；用 `j`/`k` 在列表上掠过不投。
4. 停在一个活跃会话里持续收消息时，每条新消息把红点重新点亮，红点随消息到达的那一页再次落下。

## 行为

- **触发**：一页消息到达且这一页带着未读时，投出该会话的 applink。进入会话、以及开着的会话里落入新未读，走的是同一条路径——客户端的红点随每条新消息重新亮起，清红点不是一次性动作。
- **未读的判据**：`is_read_remote = 0`、`local_read_at = 0`、非 thread 回复、未撤回，与会话列表徽标同一口径。判断读的是页面查询时的状态，不是当前徽标——本次访问自己的写入会把徽标抹成 0。
- **投出次数**：由未读消息条数决定，不由重载次数决定。每次投出对应的那批未读会在同一时刻被记为本地已读，下一页因此不再命中。
- **焦点**：applink 一律以后台方式投出。`o` 键是另一回事——它是「我要去飞书」，照常前置窗口。
- **失败**：`open` 失败时在状态行提示。红点没落下不影响 larkim 自己的徽标，`local_read_at` 已经写好了。

## 边界

- **thread 回复的红点清不掉。** applink 打开的是会话主消息流，客户端不会因此渲染 thread 内的回复，回执也就不翻。larkim 的徽标本来也不计 thread 回复，两边口径一致；chat 消息流里混着的 thread 回复因此不作为投出 applink 的理由。
- **飞书客户端的「当前会话」会跟着 TUI 走。** 切回飞书时停在最后清过红点的那个会话。
- **客户端没在运行时 applink 会把它拉起来。** 桌面端常驻是这个工具的前提，不为此做探测。
- 无 CLI 入口、无配置开关：清红点是「读了」的一部分，不是一个可选动作。
