# Read sync — 需求

larkim 里读过的会话，飞书桌面端的红点跟着落下来。

## 背景

读状态此前只有一个方向：飞书 → larkim。`read_state.is_read_remote` 由轮询拉回，翻转的时机是用户在飞书客户端里看过那条消息；`local_read_at` 补上另一半，让在 larkim 里读过的会话徽标能落下来，因为飞书 OpenAPI 没有 mark-read。

反方向是空的，代价落在客户端那一侧：在 larkim 里读完一屏，飞书的红点原样亮着，Dock 角标照样堆。`docs/chats-list/PRD.md` 的验收标准是「扫一眼 larkim 的会话列表就能分活，不必切回飞书客户端确认」——这条在 larkim 侧成立，却把飞书的角标变成了一个只能靠定期回去点一遍才消得掉的噪声源。

OpenAPI 没有把会话标记为已读的接口。清红点的杠杆是 web client 的 `PutReadMessages`：带会话的已读水位，一次请求收掉该会话此位置之前的全部未读，并当场答复成没成。认证是 `mark_read.browser` 所指的浏览器里的飞书 web 登录。

## 验收标准

1. 在 TUI 里进入一个有未读的会话，飞书客户端该会话的红点消失、Dock 计数下降。
2. 全程桌面客户端不参与：窗口不前置、不导航、不切 Space，键盘焦点留在终端。
3. 会话没有未读时不发清红点请求；用 `j`/`k` 在列表上掠过不发。
4. 停在一个活跃会话里、视野在消息流末尾时持续收消息，每条新消息把红点重新点亮，红点随消息到达的那一页再次落下。
5. 在会话里往上翻历史时落进来的消息不算读：会话列表的未读数继续涨，飞书红点保持亮，消息上带未读标记。滚回末尾时一并落下。
6. 终端失焦时落进来的消息同样不算读，回到终端、且视野在末尾时才落。
7. 一次动作就能把整份列表的红点清掉：按下后依次 POST 每个还欠着会话的已读水位，Dock 归零，larkim 不失焦。网关拒绝或对不上会话而漏掉的，再按一次会重试。

## 行为

- **触发**：会话页面正摆在读者眼前、且页面上还有没收下的未读时，把这批未读记为本地已读并向 web gateway 提交该会话的已读水位。「摆在眼前」是终端有焦点、消息面板停在消息流末尾、没有搜索/Mentions 面板或帮助层盖住它、终端也没窄到把它折叠掉。进入会话、开着的会话里落入新未读、从历史滚回末尾、切回终端，走的都是这一条路径——客户端的红点随每条新消息重新亮起，清红点不是一次性动作。
- **未读的判据**：发不发清红点看 `is_read_remote = 0`、`local_read_at = 0`、非 thread 回复、未撤回，与这次访问记为已读的那一批**相等**——静音的消息两边都在内，见 [silence](../silence/TECH.md)。会话列表的徽标在此之上再排掉静音的，所以徽标是 0 的会话这里仍可能有红点要清。thread 回复两边都不算：会话页把它们折进根消息那一行，页面上一条都没有，它们由打开话题面板时结算。判断读的是页面查询时的状态，不是当前徽标——本次访问自己的写入会把徽标抹成 0。
- **次数**：由未读消息条数决定，不由重载次数决定，也不由视野来回滚动的次数决定。每次清红点对应的那批未读会在同一时刻被记为本地已读，下一页因此不再命中。
- **`o` 键**：「我要去飞书」，用 `lark://` 前置桌面客户端，不经清红点杠杆。
- **失败**：gateway 拒绝或未匹配时在日志里记；红点没落下不影响 larkim 自己的徽标，`local_read_at` 已经写好了。

## 批量

会话列表表头右侧有一个双勾按钮，命令行有 `:read-all`，CLI 有 `larkim read-all`。三个入口同一条路径：先查出还欠着的会话，再把**所有**未读（thread 回复也在内）记为本地已读，然后依次 POST 这些会话的已读水位。

- **按下即做**：三个入口都不二次确认。按钮与 `:read-all` 按下就写，状态行先给 `marking read…` 再报结果；CLI 的 `--dry-run` 只数不写。
- **按钮常驻**：不按未读数开关。表头的上标数字把免打扰排除在外、徽标查询把本地静音排除在外，按任何一个开关都会在「只剩这两类未读」时恰好把按钮收走——而那正是最想按它的时刻。徽标全是 0 但客户端还欠着（上一次没落到）时同理：那一按是真的要清东西。没有东西可清时按下回一句 `nothing waiting in Feishu`，这句话只替飞书回答。
- **水位**：每条请求带上该会话最新一条仍欠着的消息的 `position`，收掉主消息流里此位置之前的未读。
- **集合**：飞书那边主消息流里仍欠着的会话，与 larkim 自己的徽标无关。在 larkim 里读过不让它出集合——读者在这边读了，客户端的红点并没有落下来。thread 回复不构成清红点理由（见边界），本地照样记为已读。免打扰与本地静音同样不影响这个集合——它们决定要不要打扰读者，不决定飞书那边还亮不亮。
- **可重试**：会话离开集合的唯一判据是飞书报它已读。gateway 失败或未匹配的留在集合里，再按一次就重试。仍然当场报出「N 个没清掉」——读者按下的那一刻就该知道，而不是等下一次按才发现。
- **收尾**：读者当前打开的会话排在队列最后。

## 投出的节奏

所有清红点走同一条队列（`clearQueue`），间隔 `larkweb.Pace`（100ms）逐条 POST。read gate 一次压一个，批量清理一次压一批，两者共用这一条队列，避免一次 sweep 对 gateway 形成未测过的突发。

队列只延后、不丢弃：次数仍由未读消息条数决定。冷却窗口是另一回事，它会让落在窗口内的消息被本地已读静静收掉、清红点再也不发，因此不做。

`Esc` 停下进行中的批量清理，清空它的队列。读者自己阅读带出的那一条不在此列：本地已读已经落了，丢掉它就等于上面否掉的冷却窗口。

## 边界

- **thread 回复的红点清不掉。** 只收主消息流的水位，不带 thread 的。larkim 的徽标本来也不计 thread 回复，两边口径一致；chat 消息流里混着的 thread 回复因此不作为清红点的理由。
- **跳到历史中间不算读。** 从搜索命中或 `:mentions` 跳进会话、光标落在一条旧消息上时，它下方的未读照旧亮着；滚到末尾才落。
- **未读标记比未读数活得久。** 滚回末尾把会话记为已读之后，消息上的 `●` 仍留着，直到光标走过那一块——与打开会话时的行为一致，这样标记不会在读者眼皮底下熄灭。
- **不做「N 条新消息」浮标。** 会话列表的未读数一直在视野里，已经回答了「下面还有没有东西」；面板底部再加一个跳转浮标是客户端的表现形式，不是它的语义。
- **没有「清不清」的开关。** 自动清红点是「读了」的一部分，不是一个可选动作；批量清理是一个显式动作，所以有入口而没有开关。
- **要先认得这个会话。** web client 的 chat id 是数字，与 OpenAPI 的 `oc_` 不通；larkim 靠 inbox 列出的每个会话最新一条消息的发送时间与 position 对到本地会话，对上就记下，之后一直认得。从没对上过的会话（例如在 larkim 同步它之前就已移进 Done）报错、红点留着，不猜。
- **首次读 cookie 会弹 Keychain 授权。** 每个进程每个浏览器一次。
